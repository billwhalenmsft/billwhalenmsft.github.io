I get the same question in almost every customer meeting right now: "Why would we use GitHub to build our agents?" The short answer is that you don't. Here's what the harness names mean, which one to pick, and how to think about agents you've already built.

Naming update (Oct 28): Microsoft renamed the GitHub Copilot harness to the Microsoft Copilot harness. It's the same harness, with no change to capabilities or billing, and existing agents keep working as they do today. It powers Copilot Studio, Copilot Code and GitHub Copilot, and is now also available in Microsoft Foundry (public preview). The new name will appear in the product over the coming weeks.
The short version
  • A harness is the engine room of a Copilot Studio agent: the runtime between your agent's design and the AI model. It decides when to call the model, what to send it, and which tools to use.
  • The Microsoft Copilot harness is a Copilot Studio runtime, not the GitHub Copilot developer service. It shares technology with GitHub Copilot, but your data isn't sent to or processed by the GitHub Copilot developer service, and Copilot Studio's privacy, security, compliance and data-residency commitments still apply.
  • There are three harnesses: Microsoft Copilot (formerly GitHub Copilot) for complex, multi-step work; Customer Conversation (new, in preview) for customer-facing voice and chat; and standard for predictable, rule-based agents.
  • Don't move a working agent just because a new harness exists. Move it when there's a clear business benefit, and treat it as a rebuild, not a conversion.

What is a harness?

Every agent or workflow in Copilot Studio runs on a harness. You design the agent, the model supplies the reasoning, and the harness sits in between: it determines when to call the model, what to send it, how to read what comes back, and which tools to call. The harness you choose affects how the work gets done, how much you can automate end to end, which features you get out of the box, and how you're billed.

Why it used to be called "GitHub Copilot"

The old name came from the technology underneath: the harness shares underlying technology and SDK components with GitHub Copilot (the developer product). In practice, that's what lets a business agent take a goal, break it into steps, use tools and adapt as it goes, instead of only following a fixed script.

What it is not: it's not a GitHub product you have to buy, a GitHub account you need, or a path for your business data to GitHub. Microsoft's documentation is explicit that customer data isn't sent to or processed by the GitHub Copilot developer service when agents run in Copilot Studio, and that existing Copilot Studio privacy, security, compliance and data-residency commitments continue to apply.

The three harnesses at a glance

Microsoft Copilot harness

For reasoning-heavy, multi-step business processes. Takes a goal, plans the steps, calls tools across connectors, knowledge, MCP and connected agents, and adjusts when something fails. Creates and edits Word, Excel, PowerPoint and PDF files, supports skills and memory, and runs each task in a secure sandbox.

Customer Conversation harness (preview)

For customer-facing agents over voice and chat: a website chat or a phone number. A primary agent routes to specialist sub-agents, each with its own path to escalate to a human representative. Supports skills, memory and tools.

Standard harness

For rule-based agents and structured conversations where predictable behavior matters. You define the topics, prompts and paths; it draws on your prompt library and enterprise knowledge. The dependable choice for well-understood requests.

Which one should I use?

Start with the business process, not the technology. Ask these in order:

  1. Is the agent talking to your customers over chat or the phone, and does it need a clean handoff to a person? Use the Customer Conversation harness. Examples: order status, warranty and returns, a support line.
  2. Does the work run long, span several systems, handle big files, or need to recover from surprises on its own? Use the Microsoft Copilot harness. Examples: matching invoices to purchase orders and routing exceptions, preparing a customer meeting brief and deck from email, CRM and support data, or a compliance audit across years of records.
  3. Is it a well-defined, repeatable conversation where consistency matters most? Use the standard harness. Examples: HR intake and routing, an internal help desk, answers from known policy documents.

Two more things worth knowing:

  • Bigger isn't automatically better. Put a simple task on the Microsoft Copilot harness and it can over-think: more reasoning, more waiting and more Copilot Credits without a better result.
  • You can use both together. One pattern Microsoft describes: a scheduled Microsoft Copilot harness agent cleans up messy spreadsheets and SharePoint content into structured data, and the fast, high-volume standard harness agents your users talk to get better answers from it.

"Can we convert our existing agents?"

Short answer: you can rebuild them, but only do it when there's a reason.

  • A working agent doesn't need to move. Microsoft's guidance is to migrate only for a scenario-level benefit: better quality, more efficient orchestration, long-running execution, or a model or capability you need.
  • It's a rebuild, not a toggle. Agents can't be transferred between the Microsoft Copilot harness and the standard harness. Start from the outcomes the agent must deliver, inventory what your topics, flows, variables and prompts are for, then map those to instructions, skills, tools, workflows and memory. You're done when the new agent handles its core journeys, not when every old component has been copied.
  • Some building blocks change names. In the Microsoft Copilot harness, prompts are replaced by skills, and topics and system triggers are replaced by hooks. A few features differ too. For example, Azure AI Search as a knowledge source isn't supported there, and computer use is planned. Check the features you depend on before you start.
  • There's tooling to help. Microsoft's open-source copilot-studio-plugin helps create, validate and migrate classic agents to the Microsoft Copilot harness. It's a work in progress, supported through GitHub Issues, and needs Power Platform CLI 2.9.3 or later. Always review the YAML it generates before you push it.

A word on cost

The Microsoft Copilot and Customer Conversation harnesses use Copilot Credits on a usage basis, and building, testing and evaluating an agent can consume credits too, not just running it. Plan for that. Set up the right environments and capacity controls before agents go to production, and size the harness to the job.
